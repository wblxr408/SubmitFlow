# SubmitFlow PRD

## 文档信息
- 产品名称：SubmitFlow
- 文档版本：v1.2
- 文档状态：待开发
- 更新日期：2026-04-03
- 部署形态：Docker 自部署，单实例优先，可本地直接运行
- 产品形态：PC 优先的响应式 Web 应用，移动端预留接口

## 1. 背景与目标
### 1.1 背景
面向 CS / AI 方向在校学生的实习与校招信息高度分散，用户通常同时面对三个问题：
- 不知道自己适合什么岗位方向，缺少结构化判断。
- 招聘信息分散在官网、聚合平台、公开内推页和私域链接里，筛选成本高。
- 海投后进度散落在邮箱、聊天工具和不同官网里，难以统一追踪。

### 1.2 产品目标
本产品围绕以下三个目标构建闭环：
- 帮助用户明确适合自己的岗位方向。
- 帮助用户从大规模岗位池中快速筛出优先投递目标。
- 帮助用户统一管理投递状态、提醒和后续跟进。

### 1.3 v1 核心策略
- 先做核心业务，不做完整用户登录、注册、邀请体系。
- 以单实例自用或小范围内部部署为主，后续再扩展多用户能力。
- 岗位抓取不局限于互联网公司，目标覆盖大厂、中厂、小厂，以及非互联网行业中的相关技术岗位。
- AI 能力统一由服务端编排层处理，优先采用 TypeScript 单栈实现。

### 1.4 v1 成功标准
- 用户可完成从建档到获取推荐榜单再到投递追踪的完整链路。
- 岗位池支持多来源抓取，并形成统一岗位视图与多投递入口。
- Gmail 邮件同步可以自动识别主流招聘通知并更新状态。
- Agent 能输出可解释的兴趣方向和岗位标签权重。
- 系统支持多 AI 服务商配置和按任务切换模型。

## 2. 目标用户
### 2.1 核心用户
- 本科生 / 研究生
- CS、AI、数据、系统、安全等相关方向
- 正在寻找日常实习、暑期实习、寒假实习或秋招转正机会
- 有海投需求，需要同时管理多个岗位投递进度

### 2.2 用户分层
- 新手型：不知道自己适合什么方向，需要 Agent 引导和知识图谱辅助判断。
- 海投型：希望每天快速筛一批岗位，优先关心榜单、截止日期、城市和投递入口。
- 精准型：已有明确方向，希望按标签、城市、公司、内推入口做高质量筛选。

## 3. 产品范围
### 3.1 v1 范围（必做）
- 单实例核心业务模式
- 多源岗位抓取与岗位库
- 多入口投递能力，包括官网投递、公开内推、私域内推、内部推荐入口
- 岗位推荐榜单（权重由用户自行调整）
- 投递记录管理
- Gmail 邮件同步与状态识别
- Agent 对话与知识图谱
- 多 AI 服务商配置与按任务切换

### 3.2 v1 范围（选做，预留接口）
- 飞书机器人通知
- 移动端适配（响应式布局预留，移动端交互界面暂不开发）

### 3.3 暂不纳入 v1
- 公共注册开放
- 完整用户登录、找回密码、邀请体系和组织管理
- QQ / 163 邮箱接入
- 实时抓取微信群 / 飞书群消息
- 完整的运营后台和岗位人工审核后台
- 自动绕过验证码或风控的登录方案
- 转正率社区众包闭环的完整激励体系

### 3.4 视觉与交互风格
- 整体风格采用简约、克制、留白充足的设计语言。
- 颜色以黑、白、灰为主，强调高对比和清晰层级。
- 重点信息采用线框、粗细对比和间距控制，不依赖高饱和彩色。
- 页面要避免信息墙式堆叠，优先可读性与快速扫描。

## 4. 角色与权限
### 4.1 v1 使用模式
- v1 默认为单实例模式，不对外开放公共注册。
- 系统保留未来多用户扩展的字段和概念，但首版不交付完整登录流程。
- 部署方通过环境配置或反向代理保护后台入口和敏感设置页。

### 4.2 管理员
- 管理单实例配置
- 配置 Gmail、飞书、AI 服务商
- 维护标签库与知识图谱种子数据
- 管理抓取来源配置
- 查看抓取运行记录与系统异常

## 5. 核心用户旅程
### 5.1 首次使用
1. 管理员完成 Docker 部署并进入系统。
2. 用户补充学校、专业、毕业年份、目标城市、实习类型。
3. 用户进入 Agent 流程或手动配置兴趣标签。
4. 系统生成初始推荐榜单。
5. 用户浏览岗位详情并选择投递入口。

### 5.2 海投管理
1. 用户从岗位详情页点击投递链接。
2. 用户标记已投递并选择投递入口。
3. 系统创建投递记录，默认状态为 `screening`。
4. Gmail 定时同步识别后续笔试、面试、拒信或 Offer 通知。
5. 系统写入状态历史。飞书通知为选做功能（Gmail 同步后可触发）。

### 5.3 方向调整
1. 用户与 Agent 多轮对话。
2. 系统生成用户画像与兴趣标签权重。
3. 用户在知识图谱上点击路径或手动调权。
4. 推荐榜单实时刷新。

## 6. 功能需求
### 6.1 模块 A：岗位聚合与岗位库
#### 6.1.1 目标
将公开岗位、公开内推、私域内推、登录后平台岗位归并为统一岗位池。

#### 6.1.2 功能点
- 支持多来源抓取。
- 抓取范围不限制于互联网公司，需覆盖互联网、制造业、消费品、金融、汽车、能源、游戏、医疗等行业中包含相关技术岗位的公司。
- 支持母公司、子公司、事业部、品牌别名的统一归并和搜索。
- 支持岗位去重和 canonical 归并。
- 支持同一岗位挂多个投递入口。
- 支持岗位状态管理：有效、过期、失效。
- 支持标签筛选、城市筛选、实习类型筛选、是否可内推筛选。
- **支持粘贴文本 AI 智能解析内推信息（识别公司名、内推码、投递链接），支持用户预览和选择性导入。**

#### 6.1.3 岗位展示字段
- 公司名称
- 母公司 / 品牌别名
- 岗位名称
- 细分方向
- 标签列表
- 城市
- 是否远程
- 实习类型
- 截止日期
- 紧迫性
- 综合评分
- 来源类型
- 可用投递入口列表

#### 6.1.4 投递入口要求
- 一个岗位可有多个入口。
- 入口类型包括：官网、公开内推、私域内推、内部推荐。
- 默认展示优先级：内部推荐 > 私域内推 > 公开内推 > 官网。
- 私域入口仅创建者本人可见。

#### 6.1.5 验收标准
- 同一岗位来自不同来源时，前台仅展示一个岗位详情页。
- 用户可在岗位详情页看到全部可用入口。
- 私域入口不会泄露给其他用户。
- 搜索公司别名、子品牌或事业部名称时能命中对应岗位。
- **粘贴文本 AI 解析能正确识别常见格式的内推信息，用户可预览解析结果并选择性导入。**

### 6.2 模块 B：Agent 匹配与知识图谱
#### 6.2.1 目标
帮助用户明确适合的岗位方向并生成可用于排序的兴趣权重。

#### 6.2.2 对话采集项
- 编程语言熟练度
- 技术栈偏好
- 项目经验
- 论文 / 竞赛背景
- 目标城市
- 目标实习类型
- 感兴趣方向
- 不感兴趣方向

#### 6.2.3 输出结果
- 用户画像摘要
- 标签权重列表
- 推荐方向路径

#### 6.2.4 知识图谱
- 三层结构：大方向 -> 中类 -> 细分岗位
- 节点支持点击、路径高亮和多路径选择
- 用户手动调整优先于 Agent 推荐

#### 6.2.5 验收标准
- Agent 对话结束后生成结构化画像结果。
- 图谱操作后推荐榜单实时刷新。
- 用户重新进入页面时可恢复最近一次画像和权重。

### 6.3 模块 C：岗位推荐榜单
#### 6.3.1 目标
根据用户画像和权重配置，从岗位池中生成分层推荐列表。

#### 6.3.2 榜单层级
- Top 20：强烈推荐
- Top 21-50：高度推荐
- Top 51-100：主要投递池
- Top 101-200：备选池

#### 6.3.3 评分维度
- 公司知名度
- 岗位匹配度
- 城市匹配度
- 截止紧迫性
- 转正率

#### 6.3.4 权重规则
- 用户可自由调整五个维度权重。
- 提供三个预设模板：求稳型、海投型、精准匹配型。
- 总和不要求等于 100，系统自动归一化。
- 当转正率为空时，该维度不参与本次计算。

#### 6.3.5 交互要求
- 支持实时排序刷新。
- 支持展示“为什么推荐”。
- 支持仅看可内推岗位。

#### 6.3.6 验收标准
- 用户调整权重后榜单在当前页实时更新。
- 无转正率数据时不会导致分数异常。
- 城市权重变化会显著影响排序结果。
- “仅看可内推岗位”过滤结果正确。

### 6.4 模块 D：投递追踪
#### 6.4.1 目标
统一管理用户的投递记录、状态变化和跟进提醒。

#### 6.4.2 状态定义
- `screening`
- `written_test`
- `interview`
- `offer`
- `rejected`
- `withdrawn`

#### 6.4.3 功能点
- 岗位详情页一键标记已投递
- 投递记录列表 / 看板
- 手动更新状态
- 私有标签
- 状态历史查看

#### 6.4.4 验收标准
- 创建投递记录时必须绑定具体入口。
- 每次状态变化都记录历史。
- 用户可筛选某类状态下的投递记录。

### 6.5 模块 E：Gmail 邮件同步
#### 6.5.1 目标
通过邮箱自动识别招聘邮件并同步投递状态。

#### 6.5.2 功能点
- Gmail OAuth 授权
- 每小时定时同步
- 用户手动触发同步
- AI 解析邮件主题、发件人、正文
- 状态自动更新或进入待确认队列

#### 6.5.3 阈值规则
- 置信度 > 0.8：自动更新
- 0.6-0.8：待用户确认
- < 0.6：忽略并记录日志

#### 6.5.4 验收标准
- 邮件识别到状态变化时能正确更新投递记录。
- 低置信度邮件不会误改状态。
- 重复邮件不会重复生成事件。

### 6.6 模块 F：飞书通知（选做）
#### 6.6.1 目标
在投递状态变化时，及时向用户推送提醒。

#### 6.6.2 功能点
- 飞书自定义机器人 Webhook 配置
- 状态变化消息推送
- 测试消息发送

#### 6.6.3 通知内容
- 公司名
- 岗位名
- 状态变化
- 投递入口或来源提示

#### 6.6.4 验收标准
- 用户可在设置页完成 Webhook 配置与测试。
- 自动状态变化时会触发飞书通知。

### 6.7 模块 G：AI 服务商配置
#### 6.7.1 目标
允许用户接入多种 AI 服务商，并按任务选择默认模型。

#### 6.7.2 首批接入范围
- GPT / OpenAI
- Claude / Anthropic
- GLM
- Qwen
- MiniMax
- Kimi
- Mimo
- DeepSeek

#### 6.7.3 任务类型
- Agent 对话
- JD 自动打标
- 邮件解析
- 岗位摘要生成

#### 6.7.4 功能点
- 用户录入 API Key 和 Base URL
- 启停某个服务商
- 选择某任务的默认服务商与模型
- 连接测试
- Agent 会话内临时切换模型
- 核心业务中的 AI 调用统一由服务端编排层处理，不在前端直接调用第三方模型 API

#### 6.7.5 验收标准
- 用户保存的 AI 配置只对本人可见。
- 结构化任务仅可使用支持结构化输出的模型。
- 请求失败时能看到错误状态和调用记录。

## 7. 非功能需求
### 7.1 性能
- 岗位列表在 1000 条规模下，常规筛选响应时间不超过 1 秒。
- 推荐榜单切换权重后 1 秒内完成刷新。
- Agent 首次响应目标控制在 8 秒内。

### 7.2 安全
- AI Key、OAuth Token、飞书 Webhook 全部服务端加密存储（AES-256-GCM）。
- 单实例模式下通过服务端权限控制与环境级访问保护保证安全。
- 私域入口和私有标签仅本人可见。
- 加密主密钥通过环境变量注入，不硬编码。

### 7.3 可用性
- 邮件同步和抓取任务需要失败重试与错误提示。
- 会话失效时给出明确的重新授权入口。

### 7.4 可观测性
- 记录抓取日志、AI 调用日志、邮件解析日志、状态更新日志。
- 后台任务失败时支持告警（选做）。

- 推荐榜单点击率
- 平均每周投递岗位数
- Gmail 绑定率

### 8.2 质量指标
- 岗位去重准确率
- 公司实体归并准确率

- 抓取成功率
- AI 请求成功率
- 飞书通知到达率（选做）

## 9. 里程碑
> 注：所有里程碑中的代码实现由 AI 辅助完成，代码质量由 AI 保证。

### M0：基础部署与核心骨架
- 完成 Docker 化部署（web + worker + postgres，无 Redis）、基础数据模型、AI 编排层与单实例访问保护

### M1：数据抓取与岗位库
- 完成多源抓取、公司归并、岗位详情、入口归并、首轮全量导入

### M2：投递追踪 MVP
- 完成投递记录、Gmail 同步（Gmail 同步后可触发飞书通知，飞书为选做）

### M3：推荐榜单
- 完成五维权重（权重由用户自行调整）、模板切换、城市匹配、可内推筛选

### M4：Agent 与知识图谱
- 完成对话式建档、图谱交互、标签权重联动

## 10. 风险与依赖
- 登录平台可能存在验证码、风控和条款限制，需依赖人工续期。
- 私域聊天工具不适合实时抓取，v1 只能通过导入方式接入。
- 多 AI 厂商的接口兼容性和稳定性存在差异，需做好能力声明和日志追踪。
- Gmail 是首发邮箱来源，国内邮箱需后续补接。
- 全行业抓取会增加公司归并和别名维护复杂度，需要补充公司实体标准化能力。

## 11. 发布建议
- 发布顺序建议为：抓取与投递追踪 -> 推荐榜单 -> Agent 图谱。
- v1 先用于自用或小范围内部部署，优先验证核心业务闭环，登录与注册体系后续补齐。
