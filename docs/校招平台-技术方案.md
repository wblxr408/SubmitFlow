# SubmitFlow 技术方案

## 文档信息
- 项目名称：SubmitFlow
- 文档版本：v1.2
- 更新日期：2026-04-03
- 目标：为产品 PRD 提供可直接实施的技术设计

## 1. 技术决策摘要
- 部署：使用 Docker Compose 统一部署，支持本地直接运行。
- 技术栈：v1 前后端、抓取、AI 编排、邮件同步全部采用 TypeScript。
- 数据库：PostgreSQL。
- 定时调度：Node Worker 内置 setTimeout / setInterval 或轻量定时器库（如 node-cron），不依赖 Redis。
- 浏览器自动化：Playwright for Node.js。
- AI 架构：服务端 AI Orchestrator + 多 Provider Adapter。
- 访问模式：单实例优先，不做完整多用户登录流程。
- 扩展预留：Redis 接口预留，未来多实例部署或高并发场景可按需接入。

## 2. 为什么 v1 选择全 JS / TS，不嵌入 Python
- 抓取、Playwright 自动化、Gmail API、AI 调用、前后端业务都可以在 Node.js / TypeScript 内闭环完成。
- 单语言栈能减少容器数量、日志链路、部署复杂度和跨进程序列化成本。
- AI 层当前主要是模型调用、结构化输出校验、路由与回退，不需要本地训练或重型推理。
- Python 仅在后续出现重型离线 NLP、复杂实体识别或模型推理需求时，再作为独立微服务接入。

## 3. 总体架构
### 3.1 架构分层
- 前端层：Next.js 14 + TypeScript + Tailwind CSS
- 应用层：Next.js Route Handlers / Server Actions
- 数据层：PostgreSQL
- 调度层：Node Worker 内置定时器（无 Redis 依赖）
- 任务层：Node Worker（定时任务 + 手动触发任务）
- AI 层：AI Orchestrator + Provider Adapters
- 抓取层：Source Adapters + Playwright + Parser Pipeline
- 外部集成：Gmail API、飞书 Webhook（选做）、各 AI 服务商 API

### 3.2 核心模块
- Web App：页面、交互、配置与 API
- Job Ingestion Service：抓取、清洗、归并、发布
- Company Resolver：公司别名、品牌、母子公司归并
- Recommendation Engine：排序、过滤、榜单计算
- Application Tracker：投递记录、状态机、事件历史
- Email Sync Service：Gmail 拉取、邮件解析、状态更新
- Notification Service：飞书消息推送（选做，预留接口）
- AI Orchestrator：统一封装各服务商能力

### 3.3 Docker 部署形态
- `web`：Next.js 应用容器，承载前端与 API。
- `worker`：Node.js 后台任务容器，承载抓取、Gmail 同步、AI 批处理、定时任务。
- `postgres`：主数据库容器。
- 可选 `caddy` 或 `nginx`：反向代理、基础认证、HTTPS。
- 可选 `redis`：扩展预留，Redis 接口已预留，未来高并发场景可按需接入。

### 3.4 容器职责
- `web` 只负责请求处理和轻量服务端逻辑，不跑长任务。
- `worker` 独立运行定时任务和手动任务，负责抓取、解析、同步、回退重试。
- `postgres` 使用持久化卷保存数据。
- 定时调度直接在 `worker` 进程内实现（setTimeout / node-cron），无 Redis 依赖。
- Redis 接口在代码层预留，未来扩展时可平滑接入。

### 3.5 健康检查
- `postgres`：使用 `pg_isready` 或 `pg_stat_activity` 查询作为健康端点
- `web`：在 Next.js 中注册 `/api/health` 端点，检查数据库连接和 AI 服务商可用性
- `worker`：注册内部健康检查方法（检查 Playwright 浏览器进程是否存活、Gmail Token 是否有效），通过 http GET 对外暴露
- `docker compose` 中使用 `HEALTHCHECK` 指令配合 `interval`/`timeout`/`retries` 参数
- Docker Compose 服务依赖通过 `depends_on` 声明（但需注意：v1 无主动健康检查轮询机制，如有需要后续引入 Redis 后使用 `healthcheck` condition）

### 3.6 Playwright 容器化
- `worker` 镜像基于 `playwright/playwright` 官方镜像层，或在 Dockerfile 中运行 `npx playwright install --with-deps chromium`
- 容器启动时通过 `npx playwright install chromium` 安装浏览器（约 300MB），避免硬编码在镜像中
- 单个 worker 进程管理一个 Playwright Browser 实例，通过队列控制并发抓取任务
- 生产环境配置 `PLAYWRIGHT_CHROMIUM_HEADLESS=true` 减少资源占用

## 4. 前端设计
### 4.1 视觉风格
- 采用黑、米白、灰的高对比视觉体系。

### 5.10 访问控制
- v1 不做完整多用户鉴权流程。
- 系统以 `profile_id = 1` 作为默认用户运行，所有数据隔离基于 `profile_id`。
- `profile_id` 字段为未来多用户化预留，无需改动代码即可扩展。
- 对外访问通过反向代理基础认证或环境变量控制的管理员口令保护。

### 5.11 加密设计
#### 5.11.1 加密目标
以下数据必须加密存储，不得明文落盘：
- AI API Key（`user_ai_provider_configs.api_key_encrypted`）
- Gmail OAuth Token（`user_email_connections.auth_payload_encrypted`）
- 登录态凭据（`source_accounts.auth_payload_encrypted`）
- 飞书 Webhook 配置（`user_notifications.config_encrypted`）

#### 5.11.2 加密算法
- 算法：AES-256-GCM（对称加密，AEAD 模式，防篡改）
- 密钥来源：`ENCRYPTION_KEY` 环境变量（32 字节 hex 字符串，长度 64）
- 每次加密生成随机 IV，密文格式：`base64(iv + ciphertext + authTag)`

#### 5.11.3 密钥管理
- `ENCRYPTION_KEY` 通过 .env 文件注入容器，不写入代码或镜像
- v1 不引入外部 KMS，后续多用户场景可按需升级为 AWS KMS / 自建 Vault
- .env 文件通过 `.gitignore` 排除，不提交到版本控制

#### 5.11.4 实现约束
- 解密操作仅在服务端内存中完成，不向客户端暴露明文
- 所有加密/解密操作通过统一的 `CryptoService` 封装，不得在业务代码中散落
- 加密日志不记录明文，仅记录操作成功/失败和字段名

## 6. AI Orchestrator 设计
### 6.1 目标
- 统一不同服务商的鉴权、请求格式和响应格式。
- 对结构化任务提供统一 schema 校验。
- 支持任务级默认模型切换和故障回退。

### 6.2 Provider Adapter 接口
```ts
type ProviderAdapter = {
  providerKey: string;
  supports(model: string, capability: AiCapability): boolean;
  chat(input: ChatInput): Promise<ChatOutput>;
  structured<T>(input: StructuredInput<T>): Promise<T>;
  testConnection(config: ProviderConfig): Promise<TestResult>;
};
```

### 6.3 Task Router
- 任务类型固定为：
  - `agent_chat`
  - `jd_tagging`
  - `email_parse`
  - `job_summary`
- 读取 `user_ai_task_routes`
- 若任务需要结构化输出，先校验所选模型能力
- 若主调用失败且配置了备用链，按顺序回退

### 6.4 输出校验
- `jd_tagging` 输出 `tags[]`
- `email_parse` 输出 `{ company, role, status, confidence }`
- `agent_chat` 输出会话文本和最终结构化画像
- 所有结构化任务都必须做 schema 校验，不通过则视为失败

## 7. 抓取系统设计
### 7.1 Source Adapter 接口
```ts
type SourceAdapter = {
  sourceName: string;
  sourceType: 'public' | 'public_referral' | 'private_import' | 'auth_required';
  discover(ctx: CrawlContext): Promise<DiscoveredItem[]>;
  fetchDetail(item: DiscoveredItem, ctx: CrawlContext): Promise<RawJobRecord>;
  normalize(raw: RawJobRecord): Promise<NormalizedJob>;
  extractEntrypoints(job: NormalizedJob): Promise<JobEntrypointInput[]>;
  needsReauth(error: unknown): boolean;
};
```

### 7.2 来源波次
- Wave 1：官网 / 校招站 / 公开内推页
- Wave 2：公开聚合平台
- Wave 3：登录后平台 / 内部推荐系统
- Wave 4：私域导入与 Gmail 内推链接识别

### 7.3 抓取范围原则
- 不按互联网行业做来源预筛选，而按“是否存在相关技术岗位”做覆盖。
- 目标覆盖大厂、中厂、小厂，以及非互联网行业中有研发、算法、数据、Infra、安全等岗位的公司。
- 公司标准化必须支持母公司、子公司、事业部、品牌别名归并，例如以品牌名搜索时也能命中所属集团岗位。

### 7.4 抓取流程
1. 调度器创建 `crawl_runs`
2. 适配器发现列表项
3. 拉取详情并保存到 `raw_job_records`
4. 标准化岗位字段
5. 调 AI 做 JD 标签提取和摘要
6. 跑去重与 canonical 映射
7. 更新 `jobs` 和 `job_entrypoints`
8. 标记本轮未再出现的岗位和入口状态

### 7.5 登录来源策略
- 采用浏览器自动化，复用用户人工首登后的合法会话
- 只保存加密后的授权状态，不保存明文密码
- 会话失效、出现验证码或短信验证时置为 `reauth_required`
- 不尝试绕过验证码、设备校验或平台风控

### 7.6 去重策略
- 规则匹配：公司名、岗位标题、城市、实习类型、截止日期
- 文本相似度：JD 摘要或关键字段匹配
- 来源优先级：官网 > 内部推荐 > 私域内推 > 公开内推 > 聚合平台
- 冲突时保留 canonical 岗位，入口做附属挂载

### 7.7 公司实体归并
- 新增 `Company Resolver` 负责公司主名、别名、品牌名、子公司映射
- 搜索时同时命中 `name`、`alias_names`、`brand_names`
- 抓取归并优先生成标准公司实体，再将岗位挂载到标准实体下

## 8. 推荐引擎设计
### 8.1 评分公式
```text
score = sum(validMetricScore * userWeight) / sum(validUserWeight)
```

> **防御性设计**：若 `sum(validUserWeight) === 0`（用户未建档且所有权重为 0），直接返回基础分 50，不触发除零错误。
> 当所有维度权重为 0 时，同样走上述守卫逻辑。

### 8.2 维度计算
- 公司知名度：`companies.fame_score`（归一化到 0-100）
- 岗位匹配度：岗位标签与 `user_tag_prefs` 重合度
- 城市匹配度：
  - 目标城市精确命中 = 100
  - 可远程 = 90
  - 同区域或用户接受调剂城市 = 70
  - 非目标城市 = 30
  - 城市缺失 = 40
- 截止紧迫性：
  - `<=3 天 = 100`
  - `<=7 天 = 80`
  - `<=14 天 = 60`
  - `<=30 天 = 40`
  - `>30 天 = 20`
  - 无截止日期 = 30
- 转正率：直接取岗位字段，空值不参与本次计算

### 8.3 匹配度算法
- 计算用户标签权重和
- 计算岗位命中标签对应的权重和
- `matchScore = 100 * hitWeight / totalWeight`
- 用户未建档时默认给 50

### 8.4 预设模板权重
权重总和不做归一化要求，系统自动归一化后参与计算：
```
求稳型: fame=0.4, match=0.2, city=0.2, deadline=0.1, conversion=0.1
海投型: fame=0.15, match=0.2, city=0.15, deadline=0.3, conversion=0.2
精准型: fame=0.1, match=0.4, city=0.2, deadline=0.1, conversion=0.2
```
- 三个预设模板仅供参考，用户可在此基础上自由调整
- 调整后的自定义权重不保存模板名，仅保存具体数值

## 9. 投递追踪与邮件同步
### 9.1 状态机
- `screening`
- `written_test`
- `interview`
- `offer`
- `rejected`
- `withdrawn`

### 9.2 Gmail 同步流程
1. 读取上次同步时间后的邮件
2. 按发件域名、主题关键词做招聘邮件初筛
3. 调用 `email_parse` 模型提取结构化结果
4. 尝试匹配唯一 `application`
5. 根据置信度自动更新、待确认或忽略
6. 成功更新后写入 `application_events` 并触发通知推送（飞书通知为选做）

### 9.3 去重与幂等
- 基于 `message_id + user_id` 防止重复解析
- 基于 `application_id + to_status + source_ref` 防止重复事件

## 11. 安全与权限
- v1 采用单实例保护模式，不开放公共登录。
- 应用层按 profile_id 隔离私域数据与配置。
- 私域入口、私有标签、AI Key、OAuth Token 均不可跨 profile 访问。
- 所有外部凭据通过 AES-256-GCM 加密存储，详见 5.11 节。
- 管理员接口通过环境密钥或反向代理认证保护。
